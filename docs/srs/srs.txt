1. Introduction
1.1. Purpose
This Software Requirements Specification defines the functional, non-functional, data
and architectural requirements of CampusBridge. It is intended for the project team,
reviewers at Brolf Tech and anyone who tests or maintains the platform.

1.2. Product overview
CampusBridge is a web platform that joins university learning and internship placement. It
has three connected parts that share one design system, one API and one database:
1. Public website: the entry point for visitors, with navigation to sign in and register.
2. Authentication gateway: sign-in and student registration.
3. Role-based dashboards: a workspace for each of the four user roles.
The public website and the dashboards are one product. They use the same visual
identity, the same light and dark themes and the same account, so a user moves from the
public pages into a dashboard without leaving the platform.

2. Problem statement
University learning and internship placement are managed in separate, mostly manual
channels:
Learning materials, assignments and announcements are scattered, so students miss
deadlines and resources.
Instructors cannot see student progress across courses without collecting it by hand.
Internship openings are announced informally, and many students never see them.
Applications and placement decisions are kept on paper or in spreadsheets, and
students cannot see their status.
Nothing connects what a student has learned to the internships that suit them.
Students also lack one place for planning their own projects and tasks, talking to staff
and reviewing their recent activity. (UI)

unifies learning management and internship placement for students, instructors,
coordinators and administrators.

4. Scope
4.1. In scope
All DOC modules listed in section 6.
The UI-derived modules: project management, task management, messaging, activity
history, profile and preferences, quick links and navigation, global search, dashboard
analytics and the public website.
A responsive web interface with light and dark themes.
A RESTful API, a MongoDB database and Docker-based deployment.

4.2. One coherent platform
The public website is the front door of the same application, not a separate product:
One codebase and one design system serve the public pages, the authentication
pages and the dashboards.
One theme setting (light or dark) applies everywhere and is remembered for signedin users.
Public announcements shown on the website come from the same Announcements
collection that administrators manage from their dashboard.
Sign-in on the public website leads to the dashboard of the user's role.

4.3. Out of scope
Live video classes, proctored exams, online payments and tuition management.
A native mobile application. The responsive web application covers mobile use.
Integration with the university's student information system.
Partner companies logging in. They are records, not users.

12. System architecture
12.1. High-level architecture
CampusBridge is a three-tier web application: a React client, a stateless REST API and a
MongoDB database. The API, the database and the file storage run in containers started
by Docker Compose. The public website and the dashboards are served by the same

12.4. Authentication and authorization flow
1. The client sends the email and password to POST /auth/login over HTTPS.
2. The API validates the body, finds the user by lowercase email, and compares the
bcrypt hash. When the email is unknown it compares against a dummy hash, so the
timing does not reveal it. It rejects deactivated accounts.
3. The API signs a JWT containing the user id, the role and an expiry with the server
secret, and returns the token and the user.
4. The client keeps the token (storage decision: SEC-02) and sends it as a bearer token
on every request.
5. The authentication middleware verifies the signature and the expiry and attaches the
user to the request.
6. The authorization middleware checks that the route allows the user's role. The service
layer then checks ownership: the assigned instructor of a course, the owner of a
project, the participant of a conversation.
7. A 401 response makes the client clear the session and open the sign-in page. A 403
response shows an access-denied message.
8. Signing out clears the token on the client. Server-side revocation is a proposed
enhancement (PROP).

12.5. Database architecture
One MongoDB database holds all collections (section 13). Mongoose defines the
schemas, defaults and validation. MongoDB runs as a single-node replica set in Docker
Compose, because multi-document transactions need a replica set. Uploaded files live in
a mounted volume or an object store, and the database stores only their metadata.

13.1. Design principles
Reference when documents are shared, grow without limit or change on their own:

13.4. References and transactions
References are stored as ObjectIds and checked by Mongoose before a write. Populating
them in queries is limited to the fields the screen needs.
MongoDB guarantees atomic updates of a single document. A transaction (Mongoose
session.withTransaction ) is used only where several documents must change together

or not at all:

13.5. Validation and integrity
Mongoose schemas define types, enumerations, required fields, lengths and
patterns.
Unique indexes enforce the rules that must never be broken, even by a race: one
account per email, one enrollment, one submission and one application per student
and target.
The service layer checks rules that need other documents: instructor ownership,
status transitions, deadlines and permitted message pairs.
Database-level JSON Schema validators for the critical collections are a proposed
addition (PROP).
Courses are archived rather than deleted, so history stays consistent.

Contract first. The API is described in one OpenAPI file in the repository and in a
Postman collection. Frontend and backend develop against it. After the freeze on day
3, a change needs a pull request that both sides approve.

and responses are generated from the OpenAPI file and shared with the frontend.
Mocks until ready. The frontend uses a mock layer for endpoints that are not yet
built, and switches to the real API one module at a time.
Integration checkpoints on days 7, 14 and 21: the two backend and two frontend
developers run the complete flows together.
